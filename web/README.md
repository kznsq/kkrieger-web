# .kkrieger in the browser

This runs the 2004 release of **.kkrieger** (.theprodukkt, Breakpoint 2004) in a web browser, straight from the original executable `pno0001.exe`. The page unpacks the executable, reads the game data inside it, and plays it with Farbrausch's published player code compiled to WebAssembly. Graphics go through WebGL 2 and sound through Web Audio.

The executable is not included. Drop your copy of `pno0001.exe` (from the `kkrieger-beta.zip` release) onto the page.

## Running it

```sh
python3 serve.py            # serves this folder on http://127.0.0.1:8737 with caching switched off
```

Open http://127.0.0.1:8737/ and drop `pno0001.exe` onto the page. Generating the textures, meshes and sound takes about 8 to 15 seconds. After that, click the picture to start (the click also starts the sound and captures the mouse).

- **Intro**: plays for about 97 seconds. Enter, Space, Esc or a click skips it to the main menu.
- **Menus**: arrow keys to choose, Enter to confirm.
- **Game**: W A S D to move, the mouse to look around, the left button to shoot, Space to jump, 1 to 5 for weapons. Esc releases the mouse and opens the in-game menu (continue, restart, quit).
- **Sound** can be switched on and off with the button below the picture.

URL options:

- `?exe=pno0001.exe` loads the executable from the server instead of a dropped file (for local testing; put a copy or a link next to `index.html`).
- `?mute` starts with the sound off.
- `?debug` loads `debug.js`, rendering and collision diagnostics driven from the browser console (see the comment at its top).
- `?kx` loads `kkrieger3383.kx` instead, an unfinished development build of the game exported from the published editor source. This is **experimental**: its intro and menu work, but its game view renders white (see "Known gaps").

## Building

The build needs a Clang with the WebAssembly target (`~/llvm-install/bin/clang++` and `wasm-ld` in `build.sh`). From the folder above this one:

```sh
SRCS="$(cat web/objs.txt)" LINK=1 web/build.sh          # compiles what changed, links web/kkrieger.wasm
FORCE=1 SRCS="$(cat web/objs.txt)" LINK=1 web/build.sh  # rebuilds everything (needed after header changes)
```

## How it works

1. **Unpacking** (`kkload.cpp`, `KKUnpack`): the executable is packed with an early version of kkrunchy. The decoder is a C++ port of the unpacking code in the executable's start-up stub (an adaptive range coder with LZ matches).
2. **Reading the 2004 data** (`kkload.cpp`, `KKLoad2004`): the game data is an operator graph in an early version of the werkkzeug3 export format. The loader converts it to the operator layouts of the published source, which is about a year younger.
3. **Running the operators**: the published player code (`../*.cpp`) generates all textures, meshes, materials and scenes, then runs the game logic each frame. The original calls operators through the x86 stack; `thunks.inc` (generated by `tools/genthunks.py` from the player's operator list and Farbrausch's class table) has a typed call wrapper per operator class instead.
4. **Graphics** (`web_system.cpp`, `glbackend.js`): the Direct3D 9 calls become WebGL 2. The game's vertex shaders (vs_1_1) and pixel shaders (ps_1_1 to ps_1_4), which the engine generates as Direct3D bytecode, are translated to GLSL at load time. Render states, stencil shadows, render targets and the post-processing passes map onto their WebGL equivalents.
5. **Sound** (`v2/`, `kkv2.cpp`, `kkworker.js`, `index.html`): the music and sound effects are rendered by Farbrausch's V2 synthesizer (its later C++ version, public domain). The music is rendered in the worker slightly ahead of playback and played by an AudioWorklet; sound effects are short buffers played by handle, with 3D placement for the ones the game positions.
6. **Threads**: everything runs in a Web Worker drawing into an OffscreenCanvas, so the long generation step does not freeze the page.

## What had to change, and why

The engine files in `..` are copies of `werkkzeug3_kkrieger` from Farbrausch's `fr_public` release. The tag `pristine` marks them unchanged, so `git diff pristine -- ':!web'` shows every change made to the engine.

**Platform**

- WebAssembly has no x86: inline assembly (MMX texture code, x87 helpers, the V2 player's 64-bit arithmetic) became C++ with the same results.
- Functions that read several by-value parameters as one array (`InitSRT(&s.x)` reading scale, rotation and translation; `(&tx)[j]` in `Mesh_Cube`; `(&l0)[i]` in the walker) relied on the parameters lying next to each other on the x86 stack. They now copy the values into an array first. Without this, scene transforms were garbage: rooms appeared rolled sideways and lit wrongly.
- The V2 synthesizer clears its state with `memset(this, 0, sizeof(this))`, which clears only a pointer's width. It worked on Windows because fresh memory from the operating system is zero; the port zero-fills the player's memory before use.
- `assert.h`, `rand` and a few math functions were added to the minimal C library in `libc/`.

**The 2004 data on the later engine** (`kkload.cpp` unless noted)

- **Tempo**: the 2004 export does not store the song tempo, which drives the intro timeline. It is read from the song's own header (89 beats per minute).
- **One root**: the later player switches between separate intro, menu and game graphs. The 2004 data has one graph in which `If` operators pick the scene by game state, so the port keeps that single root (`web_main.cpp`).
- **Camera**: in 2004 the `Viewport` operator ran its scene first, so `Camera` operators inside the scene (the intro flights, the weapon view) could set the camera. The later code reads the camera before running the scene. Viewports from 2004 data are flagged to run the scene first (`genoverlay.cpp`).
- **Start position**: the menu scene's player operator overwrites the game's start position during generation; the player is placed again once the game scene has run (`web_main.cpp`).
- **Portals**: the later player was compiled without portal processing, which the 2004 level needs to draw its sectors and their lights. The web build enables it (`engine.cpp`).
- **Fonts**: the font pages that feed the in-game text (HUD, menus, credits) were compiled out of the later player; the web build enables them (`genbitmap.cpp`). The 2004 font padding byte and the 2004 centring bit of the `Print` operator are converted.
- **HUD overlay**: the final merge blends the HUD over the game by the HUD's alpha. With 2004 data the "invert alpha" flag of that blend is honoured (`materials/material11.cpp`), and 2004 viewports clear to transparent black.
- **Intro skip**: the 2004 data only leaves the intro when its timeline ends; a key or click skips there (`web_main.cpp`).
- Operator classes whose parameter lists changed between 2004 and the published source (`Viewport`, `Text`, `Print`, `Monster`, `Cylinder` and others) are converted; parameters added later get their neutral default.

**Lighting and geometry**

- **Face culling** (`glbackend.js`): Direct3D's front faces are the ones that appear clockwise on the screen; WebGL's (with its default setting) are the counter-clockwise ones. The culling and the two-sided stencil states are translated with that in mind, including the extra reversal for render targets, which are drawn upside down. Getting this backwards hides every room seen from inside (walls and floors vanish, so the level looks unlit) and shows the inner faces of solid objects (roots and weapon barrels look inside-out, lamp caps flicker against the pillars).
- **Effect order** (`engine.cpp`): effects such as particles were sorted between the light passes, before the pass that adds the specular light stored in the destination alpha. The particles' alpha then turned them into solid white squares. They now sort after all lights, as single-pass meshes do.
- **Light list**: the engine compiled for kkrieger keeps at most 4 lights per frame, picked by distance and range. Its counter kept counting past those 4 slots, so later passes read beyond the end of the light list; the count is now capped (`engine.cpp`).
- **Dynamic geometry**: the original keeps animated meshes and shadow volumes in ring buffers that are discarded whenever they fill up, so their data never survives into a later frame. The web build discards dynamic geometry at the start of every frame for the same effect (`web_system.cpp`).
- **Depth range**: where the browser offers `EXT_clip_control`, depth uses Direct3D's 0 to 1 clip range directly instead of a conversion to OpenGL's -1 to 1 range (`glbackend.js`).

**Browser**

- Esc releases the mouse before a page can see the key, so losing the mouse capture sends Esc to the game (opening its in-game menu).
- Menus react to the last key pressed when the next frame runs; a key release arriving before that frame keeps the press, so quick taps are not lost.

## Known gaps

- **Intro look**: the 2004 intro renders with a strong gray haze. Its post-processing uses a "reverse subtract" stage (color minus image) that produces a gray floor. This may be how the 2004 intro looked; there is no reference to compare against.
- **`?kx` development build**: loads and runs its intro and menu, but its game view renders white. That snapshot predates the published code in more ways than the parameter layouts handled so far.
- **Load time**: about 8 to 15 seconds, mostly texture generation and building the collision data.
- The V2 speech synthesizer ("Ronan") is not compiled in.

## Files

| File | Purpose |
|---|---|
| `index.html` | page: file drop, start overlay, input, Web Audio |
| `kkworker.js` | Web Worker hosting the WebAssembly module; fonts, sound pump |
| `glbackend.js` | WebGL 2 back end and the shader bytecode translator |
| `kkrieger.wasm` | the compiled player |
| `web_main.cpp` | entry points called from JavaScript (load, init, frame, input) |
| `web_system.cpp`, `webgl.hpp` | the engine's system layer (textures, geometry, states, sound) on top of the JavaScript imports |
| `kkload.cpp`, `kkload.hpp` | unpacker and 2004 data loader |
| `kkthunks.cpp`, `thunks.inc` | operator call wrappers |
| `kkv2.cpp`, `v2/` | V2 synthesizer and its glue |
| `libc/` | minimal C library for the freestanding WebAssembly build |
| `serve.py` | local web server with caching switched off |
| `kkrieger3383.kx` | development build from `fr_public` (experimental, `?kx`) |
| `debug.js` | diagnostics, loaded only with `?debug` |
| `tools/genthunks.py` | regenerates `thunks.inc` (`python3 web/tools/genthunks.py /path/to/fr_public`) |
